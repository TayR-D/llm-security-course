*Module 4 · Part I — Foundations*

A chat looks structured. There's a system prompt, then the user's messages, maybe some
retrieved documents, maybe tool output. It *feels* like the model receives these as
separate, trusted channels.

It does not. Every one of them is concatenated into a single sequence of tokens and fed
to the model as one string. The role labels are just more tokens in that string. The
model was trained to *usually* treat the system portion as authoritative — but nothing
enforces it, because there is no channel boundary to enforce.

This is the root cause of **prompt injection**: if untrusted content (a web page, an
email, a tool result) lands in the same string as your instructions, it can compete with
them for the model's attention, and sometimes win.

## What the mitigations actually do

- **Delimiters** wrap untrusted content in markers ("everything between these fences is
  data, not instructions"). They help, but they are themselves just tokens — an attacker
  who can guess or inject the closing marker can break out.
- **Spotlighting / datamarking** transforms untrusted text (e.g. interleaving a marker
  character) so the model can better tell it apart from instructions. It raises the bar;
  it is not a wall.
- Neither changes the fundamental fact: **it is all one string.** That is why the modern
  defensive posture (M10, M14) assumes injection will sometimes succeed and limits what
  the model is allowed to *do* with a successful injection, rather than trying to make the
  string un-foolable.

:::tip[Security analogy]
This is the same class of bug as a WAF that normalizes input differently from the app
behind it. The guard and the consumer parse the same bytes two different ways, and the
gap between the two readings is the vulnerability.
:::
