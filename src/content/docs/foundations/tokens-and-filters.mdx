A model never sees your text. It sees **tokens** — integer IDs for chunks of bytes, produced
by a tokenizer before the model runs. A keyword filter, meanwhile, works on the raw
**string**. That mismatch is a recurring source of bypasses: transform the text so a filter's
substring match fails, while a capable model still recovers the meaning.

## Why this matters for defenses

- **Naive string filters are brittle.** Homoglyphs, zero-width characters, spacing and
  encodings all defeat substring matching while preserving meaning. This is the same bug
  class as a WAF that normalizes differently from the app behind it (M4).
- **Normalization is a real defense, not a cure.** Collapsing whitespace, mapping
  homoglyphs to their Latin forms, and stripping invisible characters raises the bar — but
  there is always another transform. Robust input screening uses *classifiers* that judge
  intent, not keyword lists (M12).
- **Capability cuts both ways.** The better a model is at decoding garbled or encoded text,
  the more an obfuscation that dodges your filter still lands on a model that understands it.

:::tip[For your own tooling]
If you build input filters for an LLM app, test them against the obfuscations above before
you trust them. A filter that only catches the plain string is theater.
:::
