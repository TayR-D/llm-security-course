Time to put it together. Your brief mirrors the hardest real problem in this space — and the one
you're closest to: a **self-hosted, multi-tenant LLM platform for security research**, running an
**open-weight model with refusals removed**, an **agent harness**, and **MCP tools**.

This is the frontier labs' trusted-access problem in miniature. Dual-use work *is* the point, so
you can't lean on the model refusing — the controls shift from refusal to **tenant isolation,
input/output screening, egress control, containment and audit**. Everything the providers build
(Parts III–IV), you now build yourself, because no provider safety net is underneath you.

## The brief

Design the safeguard architecture. Four deliverables:

1. **Threat model** — tenants, assets, and what "misuse" means on a platform where offensive
   security work is legitimate (M1).
2. **Layered design** — map the controls onto your architecture: identity/tenancy, input
   screening, output screening, agent containment, monitoring (M5, M10–M14, M18).
3. **Policy** — what's allowed for whom, and what happens on a flag (reroute? block? log?) (M13).
4. **Evaluation plan** — the test set and metrics you'll run in CI, reading recall *and*
   over-refusal (M19).

## The key insight to leave with

On an open-weight, self-hosted deployment, **the model's own refusal is the one layer you don't
have** (M3, M11). Everything protective is something you add around it — which is exactly why the
course spent Part III taking the provider stack apart layer by layer. You're rebuilding that stack
with the pieces from M18, governed by your own threat model.

That's also the honest reframe of your platform's dual-use goal: you're not trying to make the
model refuse security work (it shouldn't, for your users) — you're making sure a *compromised* or
*injected* session can't turn your tools and tenant data against you.
